# 架构设计

## 1. 项目目标与边界

### 1.1 核心目标

本项目针对 LLM Agent 在真实业务环境下的若干工程不确定性——工具调用失败、工具幻觉、权限越界、提示词注入等——构建一套具备自愈能力、多智能体路由与多层安全判定的 LangGraph 系统，旨在验证『Production-grade LLM Agent 应当具备哪些工程化设计』这一命题。

### 1.2 场景选型理由

1. 自习室有明确的业务规则，系统据此触发 `business_rule_violation` 分类、向用户合规拒答。
2. 自习室有资源争抢（座位有限），能触发 `resource_conflict`，验证乐观锁 / CAS（Compare-And-Swap）和自愈功能。
3. 有用户身份概念，验证防止用户越权，进行安全设置。
4. 既有结构化数据（座位 / 订单 SQL 表）又有非结构化数据（规章制度文档），能在同一项目内同时验证工具调用与 RAG 检索。

### 1.3 技术目标

本项目按以下三层组织技术目标：

**核心能力（项目主要卖点）**

1. **Self-Healing Agent 的工程化设计**：包含基于 LLM 的错误语义分类、Classify-then-Decide 双阶段决策、自愈次数熔断三个子机制。

**支撑能力（工程基础盘）**

1. **多层身份隔离的安全防御**:API 认证层 → 工具签名层 → 服务层的三道闸门。
2. **LangGraph 多子图编排与状态总线设计**:6 维 AgentState + 自定义 reducer + 全链路 trace。
3. **双路 RRF 融合的 RAG 检索**:BM25 字面量 + 向量语义 + LLM 自动元数据打标。

**工具集成能力**

1. **MCP 协议接入与 Service 层异常映射**:LLM 工具失败的标准化路径。
2. **完整 CRUD + 越权防护**：booking 子图实现订单的 Create / Read / Update / Delete 全流程，配套 cancel_booking 的跨表原子事务（同时更新 bookings 和 seats）+ "存在 → 归属 → 状态" 三段式校验顺序，确保越权请求不暴露资源存在性。

### 1.4 已知限制与未来工作 (Out of Scope)

本项目刻意将以下事项划在范围外，原因均为"不会触发新的架构挑战"：

| 限制项               | 现状                                                         | 升级到生产级需要补充                                         |
| -------------------- | ------------------------------------------------------------ | ------------------------------------------------------------ |
| **CRUD 完整度**      | 已实现完整 CRUD + 越权防护层。                               | 暂无需进一步升级                                             |
| **数据库并发能力**   | SQLite + WAL，可支持单机轻并发                               | 替换为支持行锁的 PostgreSQL/MySQL，并补充并发压测            |
| **多 Provider 兜底** | LLM 池仅注册 Moonshot Kimi 一个 provider                     | 架构上已通过 `init_llm_pool` 工厂函数预留扩展点，未实际验证 GPT/Claude 接入 |
| **测试覆盖**         | L1 纯函数 + L2 mock 共 86 条，覆盖自愈分类/策略表/熔断/降级、会话注册表归属隔离、历史视图过滤与 IDOR 闸门、执行轨迹摘要；集成路径手动验证 | 补充端到端 e2e 自动化（路由/子图/MCP 集成层当前仍手动黑盒）  |

## 2. 项目分层

本项目采用四层架构：

1. **用户接入层**（`api.py`, `app.py`）：接 HTTP 请求和 UI，做认证，不写业务逻辑。
2. **编排层**（`graphs/`）：基于 LangGraph，负责理解用户意图、派发到对应子图、管理对话状态和流转。是项目最复杂的一层。
3. **业务服务层**（`services/`）：把基础设施提供的原始能力包装成有业务语义的方法，注入业务逻辑（比如异常映射、RRF 融合排序）。
4. **基础设施层**（`infrastructure/`, `mcp_server/`, `data/`）：提供原始能力——LLM 实例、向量库、SQLite 持久化、MCP 工具，不知道这是个自习室项目。

## 3. 核心设计决策

#### 3.1.1 问题陈述：为什么需要多层防御？

在设计带有大语言模型（LLM）的 Agent 系统时，我们很容易掉进一个“软约束陷阱”——以为只要在 Prompt 里严厉警告一句“你是当前用户，绝对不能操作别人的数据”，系统就安全了。但实际上，这种靠自然语言维持的边界非常脆弱。一旦用户的输入带有恶意引导（比如提示词注入），LLM 很容易就被绕晕，从而安全性遭到破坏。用户态（对话上下文、LLM 推断）和系统态（真实的业务操作）之间，不能只靠大模型的“自觉”来把守。

如果没有硬性的物理防御，我们的系统在真实场景下要面对非常直观的威胁：攻击者可以直接抓包修改 HTTP Body，冒用其他同学的学号；或者直接越过前端限制，用脚本疯狂调用 API 接口；甚至在正常登录后，通过特定指令诱导工具去取消别人的订单。为了彻底堵死这些漏洞，我给项目确立了一个核心底线原则：**身份的真实来源，必须由系统底层的单一可信源决定。** 前端 Body 传来的字段不算，聊天的历史上下文不算，LLM 提取推断出来的参数更不算。

**为什么多层防御体系不可省？**

因为 Agent 的执行链路很长，我们必须秉持“假设上一道防线随时会崩溃”的底线思维去设计系统，只有这样，才能保证在面临极端情况时核心业务依然安全。

#### 3.1.2 第一层：API 认证层（HMAC-SHA256 凭证化）

在技术选型上，我没有盲目使用业界常见的 JWT，而是自己设计了一个轻量级的三段式 Token：`{sid}.{timestamp}.{sig}`。用一句话解释为什么不用 JWT：在当前这种单体服务场景下，并没有跨服务联邦认证的需求，JWT 臃肿的结构只会徒增解析开销。而我设计的这个极简 Token，不仅用底层签名（sig）一举防住了伪造和篡改，还利用时间戳（timestamp）封死了重放攻击（Replay Attack）的可能。

**为什么这层 API 认证不可省？**

因为它是系统最外围的“过滤网”，如果不在这里用极低成本的密码学手段把非法请求直接掐断，它们就会长驱直入，不仅带来极大的安全隐患，还会白白烧掉我们昂贵的 LLM 推理 Token。

#### 3.1.3 第二层：工具签名物理隔离（闭包注入）

如果说第一层防的是外部，那第二层防的就是“内部被带偏的 AI”。

在常规的 Agent 开发中，很多人会直接把带有 `student_id` 参数的工具暴露给大模型，然后在 Prompt 里约束它：“只能传当前用户的学号哦。” 这种软约束在遇到“提示词注入攻击”时一击即溃，LLM 极易被诱导去构造别人的学号传给工具。

为了彻底拔除这个隐患，我引入了“闭包工厂（make_tools_for_user）”**模式。它的本质是**在物理层面从工具签名中删掉身份参数。在把工具交给 LLM 之前，系统会先用闭包把真实的 `student_id` 像“钢印”一样提前打进工具的执行逻辑里，然后动态生成一个去掉了 `student_id` 参数的新工具签名给 LLM。暴露给 LLM 的工具签名里完全没有 student_id 参数——LLM 根本没有 传递该字段的机会，物理上杜绝了通过工具参数伪造身份的可能。

这样一来，在 LLM 眼里，`cancel_booking` 这个工具只需要传一个 `booking_id` 就能运行。它根本不知道底层还需要学号，自然也就失去了伪造学号的能力。配合 `dynamic_tool_node`，这种闭包模式在 LangGraph 极其复杂的跨节点流转、甚至是状态机中断恢复的持久化场景下，依然能精准捕获当前会话的合法身份，表现得极其健壮，无需再依靠大模型约束。

**为什么这层工具隔离不可省？**

因为大语言模型是不可控的黑盒。只要你不把“身份切换”的方向盘交给 LLM，它就算被用户的恶意指令彻底绕晕，也绝对开不出当前用户的数据边界。

#### 3.1.4 第三层：服务层强制使用（trusted_sid 覆盖）

有了第一层的密码学 Token 和第二层的工具闭包，第三层要解决的问题是：**这两个东西怎么安全地接合在一起？** 答案是：在服务入口（`/api/chat`）进行冷酷无情的强制覆盖。

当请求到达后端时，设计了一套“绝对不信任前端 HTTP Body”的覆盖逻辑。系统会从请求头的 Authorization 字段中验签解密出 `authenticated_sid`。紧接着，不管用户的 Request Body 里传的 `student_id` 是什么，系统一概无视，直接执行强制覆盖：`trusted_sid = authenticated_sid`，并把这个绝对可信的身份注入到 Agent 的全局状态（State）中。

在实测中，这套机制完美抗住了三种维度的越权攻击：第一种，不带 Token，直接 401 拦截；第二种，篡改 Token 伪造身份，验签失败，401 拦截；第三种最隐蔽，也就是带了自己合法的 Token，但把 Body 里的学号改成了别人的——系统会自动触发告警日志，并静默地用回 Token 里的真实身份，让攻击者的越权企图扑了个空。

**为什么这层服务层强制覆盖不可省？**

因为它是连接“底层密码学”和“上层业务 Agent”的唯一安全桥梁。如果没有这层冷酷的强制覆盖，前端传来的脏数据一旦流入 Agent 状态机，前面做的所有防御都会功亏一篑。

#### 3.1.5 第四层：操作级越权防护（CRUD 扩展中新增）

前面的第一到第三层，解决的都是“证明你是谁”的问题——防的是系统级的身份伪造。但是，就算用户合法登录了，系统依然面临另一种更隐蔽的安全威胁：操作级越权（IDOR）。比如，张三拿着自己合法的 Token 登录后，故意在自然语言里诱导 Agent 去取消李四的自习室座位。这时候，前置的身份网已经放行了，必须在具体的 CRUD 工具内部（比如 `cancel_booking`）建立最后一道防线。

在这道防线上，我设计了极其严苛的“**存在 → 归属 → 状态**”三段式校验顺序。这个顺序是底线，绝对不能反过来：必须先去数据库查数据存不存在，再去比对订单是不是当前用户的，最后才有资格看能不能改状态。如果查出试图操作别人的订单，抛出 `NotYourBookingError` 时，绝不会把它当成普通的“业务规则冲突（business_rule_violation）”去让 LLM 尝试换个参数修复，而是直接将其定性为不可恢复的最高安全级别（`unrecoverable`）。配合我们预设的自愈策略，系统会强行接管并产生静默响应，绝不向攻击者暴露诸如“这个订单是否存在”或“它当前处于什么状态”的任何业务细节，彻底掐断信息泄露的可能。

**为什么这层操作级防护不可省？**

因为它是保护用户数据资产的“最后一道保险”。就算前置的身份验证网全部失效或者被绕过，只要这层底层的归属权校验还在，用户就永远只能在自己的数据沙盒里打转，绝对碰不到其他人的核心资产。

#### 3.1.6 设计原则提炼

打完这四层防御的战役，我对系统安全架构有了一个非常深刻的工程认知：**多层防御绝不等于在单层逻辑上反复堆砌，而是建立在“假设上游随时可被攻破”的底线思维上。** 这就像俄罗斯套娃一样的纵深防御：哪怕 Body 字段被伪造，HMAC 验签层强制覆盖能拦住；哪怕 Prompt 被注入，工具签名闭包能拦住；哪怕用户合法登录后想操作他人资源，三段式归属校验能拦住。

整套防御体系的灵魂，可以浓缩为一条铁律，那就是“信任边界唯一可信源”原则——在我们的系统里，用户的身份来源有且只能收敛到代码底层的密码学验签结果。至于前端传来的 Body 字段、长篇大论的聊天上下文、甚至是 LLM 费尽心机推断出来的参数，统统视为不可信的脏数据，绝不给予任何信任。

### 3.2 Self-Healing Agent 的架构演进

#### 3.2.1 问题陈述：为什么需要 Self-Healing？

我的自习室场景下，工具调用失败有四种典型样态：资源被抢（座位 `SEAT_OCCUPIED`）、业务规则拦截（`VIOLATION_LIMIT` 违约超限）、参数越界（duration 超过 8 小时）、底层抖动（SQLite 锁库）。

这四种失败的处理路径完全不同——前两种用户能修，第三种 Agent 自己能修，第四种重试就能修。如果不显式处理，Agent 会把所有错误码当成自然语言扔回上下文里继续推理，结果要么陷入死循环，要么向用户编造一条"订单已生成"的虚假回复。Self-Healing 就是为了把这四类失败拆开，在代码层分别给出确定性的处理策略。

#### 3.2.2 V1：让 LLM 全权决策（含失败案例）

在最初的 V1 版本中，我犯了一个典型的工程错误：过度信任大模型，让 LLM 充当了全权决策者。

当时我设计了一个 `RepairDecision` 数据结构，让 LLM 在捕获异常后同时输出四项内容：

```python
class RepairDecision(BaseModel):
    reasoning: str                  # 错误推理
    action_type: Literal[...]       # 处理动作（已用 Literal 锁住选项）
    suggested_tool: str             # 建议调用的工具
    instruction_to_agent: str       # 给 Agent 的指令
```

实测中这个设计在 `VIOLATION_LIMIT`（违约超限）场景下翻车——LLM 一次推理里同时犯了两类错误：

- `reasoning`: "该限制属于业务硬规则，无法通过重试、换接口或调整参数绕过"
- `action_type`: `"retry_with_new_params"` ← 跟自己的 reasoning 直接矛盾
- `suggested_tool`: `"violation_service::query_violation_list"` ← 幻觉，编造了工具名

这次翻车让我意识到一个本质问题：LLM 极度擅长"语义分析"，但极度不擅长"确定性决策"。让它在同一个节点既做理解又下决策，分裂是必然的。

#### 3.2.3 V2：Classify-then-Decide 关注点分离

为解决 V1 的幻觉和自相矛盾，我重构了整个决策链路，核心动作是：剥离 LLM 的决策权，只保留其分类权。

我将 `RepairDecision` 替换为 `ErrorClassification` 结构，砍掉了负责决策的 `action_type` 和自由发散的 `suggested_tool` 字段。现在，LLM 只需要回答"这是什么类型的错误"：

```python
class ErrorClassification(BaseModel):
    reasoning: str
    category: Literal[
        "business_rule_violation",
        "resource_conflict",
        "invalid_params",
        "transient_failure",
        "unrecoverable"
    ]
    user_facing_summary: str
```

被剥离出的决策权，在代码层引入的一张静态字典 `REPAIR_STRATEGY_MAP` 接手。LLM 输出 `category` 后，代码查表给出确定性策略：

```python
REPAIR_STRATEGY_MAP = {
    "business_rule_violation": {
        "should_retry": False,
        "instruction": "向用户解释原因，禁止重试..."
    },
    "resource_conflict": {
        "should_retry": True,
        "instruction": "使用 search_free_seats 查询可用资源..."
    }
}
```

我把这种架构称为 Classify-then-Decide（先分类后决策）。它的本质洞察是：让 LLM 分类错误类型，让代码回答如何解决。因为 `category` 被 `Literal` 严格锁死，LLM 无法编造不存在的错误类型；而因为策略表是硬编码的，分类结果一旦落地，下游的重试与兜底行为就不再受大模型幻觉的影响。

#### 3.2.4 V3：Prompt 边界锚定（含失败案例）

V2 改完后，我以为问题彻底解决了，但在第二个测试场景就翻车了。

在测试"座位被抢"（`SEAT_OCCUPIED`）错误时，LLM 给出的分类竟然是 `business_rule_violation`。它的推理逻辑是："座位状态不对，这属于业务规则层面的冲突"。

这次翻车暴露了一个隐蔽的问题：即使 Literal 锁死了输出空间，LLM 对这些概念的**语义边界**依旧会出错。在它的语料认知里，"资源不可用"和"违反业务规则"被混为一谈。如果分类第一步错了，V2 精心设计的策略表就会把系统带向深渊——判定为业务违规会直接熔断并拒答，而实际上这只是资源冲突，调工具换个座位就能解决。

针对这个问题，我在 `error_analyzer_node` 的系统 Prompt 中引入了边界锚定，构建了四层防御：

1. **头对头对比**：明确界定 `business_rule` 针对的是"用户身份/账户状态"，而 `resource_conflict` 针对的是"所请求的物理资源"。
2. **判断口诀**：强行注入一个思考锚点——"换个对象（如换个座位）重试有用吗？"有用就是资源冲突，没用就是业务限制。
3. **反例对照**：直接在 Prompt 里写死特例（明确指出 `SEAT_OCCUPIED` 几乎必然是 `resource_conflict`）。
4. **兜底偏置**：规定拿不准时优先选 `unrecoverable`（保守策略，宁可误终止不可误重试）。

#### 3.2.5 V4 演进方向：用代码确定性短路 LLM

V3 跑通后，self-healing 链路在功能上已经闭合，但在原则上还有一处未贯彻的地方。

每一次工具调用失败，error_analyzer_node 都会触发一次 LLM 调用来做错误分类，即便这个错误是系统中早已定义好的已知异常（如 SEAT_OCCUPIED、VIOLATION_LIMIT），耗费Token。 对于每一个在 BookingDomainError 中已经携带了明确 category 元数据的异常，V3 仍然绕了一大圈——把代码已经知道答案的结构化元数据，交给 LLM 用自然语言重新推理一遍，再得出一个原本查表就能得到的答案。V2 已经把决策权交还给代码，但 V3 在分类那一步又把不确定性引了回来——原则只在部分路径上贯彻，不算成立。

顺着这个反思往下看，V3 中 LLM 的冗余其实不止"分类"一处。V3 让 LLM 在 ErrorClassification 中同时输出 category 和 user_facing_summary，背后的设计假设是——工具层抛出的错误是给开发者看的技术描述，需要 LLM 翻译成用户能理解的语言。但回看 mcp_server 的实际实现，所有 message 字段本就是用户友好的中文描述（如"座位 1 当前已被占用"），LLM 的翻译职责从一开始就不成立。这是 V3 时期一个从未被审视的潜在假设——不是实现层面的疏漏，而是设计层面的错误前提。

为此，V4 做了三处协同改动：

1. **工具层透传元数据（带外结构化）**：book_seat_tool 捕获 BookingDomainError 时，把 e.category.value、error_code、message 写进 ToolMessage 的 **artifact**（结构化带外信道），content 则只保留给用户看的纯友好文本（e.message，如“座位 1 当前已被占用”）。技术元数据机读、人读文本人读，彻底分离，互不污染。（早期 V4 曾把元数据内联进 [TOOL_ERROR] 字符串靠正则解析，现已收敛为 artifact；字符串路径仅作 NO_AUTH 等无 artifact 的遗留兜底保留。）
2. **error_analyzer 旁路判定（artifact 优先）**：节点定位到出错 ToolMessage 后，优先从 artifact 读结构化 category；命中 REPAIR_STRATEGY_MAP 中已知分类时，直接查策略表、跳过 LLM 调用，并用 artifact["message"] 填充 instruction_template 中的 {user_summary} 占位符。读不到 artifact（旧路径 / NO_AUTH 兜底）时，才回退到正则解析 content。
3. **未知异常降级**：仅在异常未携带 category 元数据时（如未来新增的、尚未被领域异常体系覆盖的错误），才降级到 V3 的 LLM 语义分类作为兜底。

**实测验证：**

用户预定占用座位触发 SEAT_OCCUPIED 时，日志显示"⚡ [Self-Healing V4] 异常元数据短路：category=resource_conflict（0 LLM 调用）"，trace 中 llm_called 字段为 false。所有已知业务异常（SEAT_OCCUPIED、VIOLATION_LIMIT、INVALID_PARAM 等）在 error_analyzer 阶段实现 0 LLM 调用，仅当出现未预见的底层报错时才走 LLM 兜底分类。

V4 的本质，是承认 V2 确立的"代码确定性 > LLM 不确定性"原则，只有在所有路径上都贯彻才算真正成立。至此，self-healing 链路上所有已知异常都不再依赖 LLM 参与——这也是下一节将要总结的设计原则能够立得住的真实落点。

#### 3.2.6 错误判据的统一：单一真相源与人机信道分离

V4 把元数据迁到 artifact 后，暴露出一个更隐蔽的一致性风险：“一条工具消息是否出错”这个判断，在链路里有两个地方各自做一次——嗅探器 check_tool_error 决定要不要转去自愈，定位逻辑 analyze_error 决定对哪条错误做修复。两处判据一旦不同就会撕裂：嗅探器凭 artifact["is_error"] 认定出错、转去自愈，自愈却还在 content 里找 [TOOL_ERROR] 字符串——而 content 已经被清理成纯友好文本，于是找不到，自愈对着“没有错误”空转。

解法是把判据收敛成**单一真相源**：抽出纯函数 _tool_message_is_error(m)，规则是 artifact 优先、content 回退（有 artifact(dict) 就以 artifact["is_error"] 为准；没有才回退 content 里的 [TOOL_ERROR] 字符串）。嗅探器、自愈定位、以及 trace 的错误状态判定四处共用同一函数，从根上杜绝“两处判据不一致”。

与之配套的是一条**人机信道分离**的纪律：工具错误的 content 一律是纯 e.message 友好文本，所有技术元数据（category、error_code、is_error）只走 artifact。唯一的例外是 NO_AUTH——它没有 artifact，靠 content 里保留的 [TOOL_ERROR] 字符串走回退路径，作为遗留兼容的特例显式保留。把这条判据逻辑抽成纯函数，意义和把 analyze_error 抽出闭包一致：让“什么算错误”这个触及控制流与安全的关键判断，可以被单元测试钉死，而不是散落在多处、各自演化、终将漂移。

#### 3.2.7 设计原则提炼

本项目从 V1 到 V4 的演进，本质上是为了控制大模型带来的不确定性，不断挤压大模型的自由发散空间，将控制权彻底收归确定性代码的轨迹。

LLM 在 Agent 链路中的唯一合法身份，是处理不可预见输入的"模糊语义翻译器"——负责在用户和系统报错的非结构化文本中提取结构化事实。而所有触及状态流转、动作决策和系统边界校验的操作，都必须由代码层确定性地完成。

这一原则在本项目中被彻底贯彻为三个具体动作：剥离决策权的 Classify-then-Decide 架构、用 Prompt 强制锁死认知空间的边界锚定，以及用异常元数据消除冗余推理的 V4 短路路由。每一个动作，都在剥夺 LLM 不该拥有的权力。

这件事远超出自习室场景的意义在于：它让我看清了 LLM 应用工程化的一个核心约束——系统的健壮性从来不取决于大模型有多聪明，而取决于代码的防御底线有多硬。作为一名 AI 工程师，我的工作不是去教大模型怎么做决策，而是写好那些确定性代码——哪怕大模型完全疯掉，系统也不会崩溃。

## 4. 会话管理：多轮对话的持久化与隔离

#### 4.1 问题陈述：会话状态该存在哪？

多轮对话要“记得住”历史。最省事的做法是把消息存在前端（Streamlit session_state / 浏览器 localStorage），但这是个玩具方案——刷新即丢、换设备即丢，更谈不上“我的历史会话列表”。会话状态必须落到后端持久化。

好在 LangGraph 的 checkpointer 已经按 `thread_id` 把图状态（含 messages）落盘到 `data/memory/memory.db`，服务器重启也不丢——“单条会话的记忆续接”这一层其实已经具备。但 checkpointer 解决不了两件产品级的事：第一，它没有 user 维度，无法“按用户列举他拥有的会话”；第二，它存的是引擎状态快照，不带标题、时间这类业务元数据。

#### 4.2 双层持久化：引擎状态 vs 业务元数据

这里有一个容易踩的坑：把“会话归谁、叫什么、什么时候建的”也塞进图状态让 checkpointer 顺带存。这会污染 AgentState，而且依然无法跨 thread 列举。正解是把两个职责不同的持久化层彻底分开：

- **Checkpointer（`memory.db`）**：LangGraph 内部状态，按 `thread_id` 存 AgentState 的快照序列，给图引擎“断点续跑”用。它不认识 user。
- **Session Registry（`sessions.db`）**：应用层业务元数据，按 `user_id` 存“他拥有哪些会话 + 标题 + 时间”，给产品 UI 的列表与切换用。

`thread_id` 是这两层之间唯一的 join key。这与项目里既有的两条纪律一脉相承：CQRS 读写分离（registry 是只读模型，checkpointer 是写时落下的引擎状态），以及承重墙 / 开闭原则（新能力 = 新模块新表，绝不改动图签名或 pipeline）。

#### 4.3 会话恢复的归属闸门：在新资源上的复用

会话历史端点 `/api/history?thread_id=` 是一个典型的 IDOR 攻击面。如果只验 Token 拿到 `sid` 就直接 `aget_state(thread_id)` 把状态吐回去，那么任何登录用户都能凭一个 `thread_id` 读到别人的会话。`thread_id` 是 UUID 不易猜，但“不易猜”从来不等于“已授权”——security by obscurity 不是安全。

我的处理方式和 §3.1.5 取消订单的越权防护**完全同源**：先 `verify_owner(sid, thread_id)` 过归属闸门，不过就静默拒绝（返回 404，且不区分“不属于你”和“不存在”，杜绝攻击者借 `thread_id` 探测他人会话是否存在）。授权严格先于取数，顺序不能反。这条“先校验归属、再读消息”的逻辑被抽成纯函数 `build_history_view_or_none`——归属不成立时在碰到任何消息内容之前就短路返回，与把 `analyze_error` 抽出闭包是同一种手法，让安全决策可被单元测试钉死。

同一道归属校验也守在 `/api/chat` 写路径上：带着非空 `thread_id` 来续接对话时，必须是你自己的会话才放行，否则同样 404——这堵死了“借 chat 端点往别人 thread 里灌消息”的旁路。

**为什么这层会话归属不可省？** 因为会话历史里可能含座位、订单、积分等个人数据，会话列表本身也泄露用户的行为轨迹。一旦 `thread_id` 能被跨用户访问，前面四层身份防御在“读历史”这条新链路上就被整体绕过了。归属闸门让会话恢复复用了和订单越权防护一致的安全底线。

#### 4.4 thread_id 契约：客户端不发明 id

谁来生成 `thread_id`，是个必须定死的契约。我采用的约定是**客户端不发明 id**：开启新会话时客户端不传 `thread_id`，由服务端 mint 一个 UUID、登记进 registry、并通过响应回传；客户端存下后，后续轮次再带上它。

这样 registry 就成了“thread 是否存在”的唯一真相源，归属闸门也得以保持最严格——任何服务端不认识的非空 id 一律拒。这与 OpenAI threads 等有状态会话 API 的契约一致。（一个踩过的坑：前端若自行预生成 id 并每次都发，后端会把这个非空但未登记的 id 误判成“老会话”，触发归属校验失败、返回 404；把契约统一到“新会话不带 id”之后，问题消失。）

#### 4.5 设计原则提炼

会话管理这块再次印证了贯穿全项目的两条主轴：**职责分离**（引擎状态 ≠ 业务元数据，宁可多一张表也不让两者纠缠）与**信任边界唯一可信源**（会话归属由 registry 的 user 维度裁定，而不是听信客户端传来的 `thread_id` 自证身份）。它本质上是把前面已经建立的安全与分层纪律，平移到了“多轮对话”这个新维度上。

## 5. 可观测性：让自愈与工具调用从黑箱变可见

#### 5.1 问题陈述：Agent 的执行链路天然是黑箱

前面用三章把“自愈”打磨成了核心卖点，但它有个致命的展示缺陷：**所有工具调用和异常自愈都发生在后端，UI 上什么都看不见**。用户（和面试官）在前端只能看到最终那句自然语言回复——工具到底有没有真被调用、调了哪个、成败如何、失败后又走了哪条自愈路径，全是黑箱。一个“我说它会自愈”但无从印证的系统，卖点是不可信的。可观测性要解决的就是这件事：把执行链路提炼成肉眼可见的证据。

#### 5.2 关键认知：trace 早已在状态里，缺的只是“读出与翻译”

容易想歪的方向是“再搭一套日志/埋点系统”。但这里有个更省的事实：决策链路其实**早已被记录**。AgentState.trace 由各子图节点在执行时写入（工具调用成败、error_analyzer 的每一次决策），而它的 reducer 是定制的 merge_trace——一个哨兵机制：节点返回 [{"_reset": True}, {...新记录...}] 时丢弃旧值、只留本轮，从而实现**轮次级清零**而不破坏 LangGraph“节点只返回 patch”的约束。

这条性质很关键：因为 trace 每轮清零，所以请求结束时一次 aget_state(config) 读回的 trace，**恰好就是“本轮”的完整链路**，无需按时间切分、无需追加过滤。可观测性因此不是“新增写路径”，而是“把已经落在状态里的东西读出来、翻译成人看得懂的步骤”——零侵入，不动任何子图签名。

#### 5.3 摘要器作为纯函数：展示数据也要可测试

翻译这一步抽成模块级纯函数 summarize_execution_trace(trace) -> dict，刻意放在 utils/（仅依赖 stdlib，不引 langgraph / mcp 重依赖）。它把原始 trace 提炼成四类有序展示步骤——🛠 工具调用（成 / 败）、⚡ V4 0-LLM 短路命中（已知异常查表，0 次 LLM 调用）、🧠 LLM 降级分类（未知异常兜底）、🔥 熔断触发（重试达上限强制停止）——并同时算出结构化指标 tool_call_count / shortcut_count / llm_classify_calls / circuit_broken / has_activity。

把它做成无副作用纯函数是有意为之：**展示数据是响应契约的一部分**，“调了几次工具、是否自愈、短路省了几次 LLM、是否熔断”这套叙事的正确性值得被单元测试钉死。这与把 analyze_error 抽出闭包、把 build_history_view_or_none 抽成纯函数是**同一种手法**——凡是承载关键语义的逻辑，都从框架与 I/O 中剥离出来，让它可独立验证（本模块配套 L1 +14 条）。

#### 5.4 响应契约与降级：可观测性绝不拖累主响应

/api/chat 在生成回复后，于末尾 aget_state 读出本轮 trace、过摘要器、塞进 ChatResponse.activity（空字典表示本轮无活动，前端据 has_activity 决定是否渲染面板）。

关键在于**这整段读取被 try/except 包裹**：可观测性是锦上添花，对话本身才是主干，轨迹摘要一旦出任何岔子（状态读取失败、字段缺失），绝不允许它拖垮用户真正要的那句回复——失败就退化成“没有面板”，主响应照常返回。此外面板是 live-only：历史消息回放时不重建轨迹，避免给“读历史”这条只读链路凭空造出本不属于它的执行记录。

#### 5.5 设计原则提炼

可观测性这一章把全项目的纪律又验证了一遍，落点有三：其一，**它是读模型而非新写路径**——复用已落在状态里的 trace，零侵入地读出来，与 §4 的 CQRS 读写分离一脉相承；其二，**展示数据也是契约**，值得像安全逻辑一样被纯函数测试钉死；其三，**降级隔离**——辅助能力的失败不得污染主干，这是把“防御底线”从自愈链路平移到了响应链路。

它最终兑现的，是把整个项目最硬的卖点变得**可证**：自愈不再是一句“它会自己恢复”的口头承诺，而是前端一行行看得见的证据——“调用 get_my_bookings ✅ → 调用 cancel_booking ❌ → ⚡ 资源冲突，命中策略表 0 次 LLM 调用 → 重试 ✅”。一个能被肉眼复核的系统，才是一个可信的系统。
